# Project Dev

本项目的开发主入口，由 `project-skill-manager` 生成。日常开发新功能/修bug/做优化，从这里开始，全程陪你把需求聊清楚、把代码写出来、把文档同步好。读写的都是 `.claude/project-meta/` 下的数据，不针对项目做代码定制。

## 调用后先了解背景

1. 读 `.claude/project-meta/index.md`（模块清单 + 模块复杂度元数据）和 `skills-index.md`（可引用的 rule-skill 清单）
2. 如果项目根存在 `CLAUDE.md`、`.claude/memory/`、`.claude/rules/`，顺带扫一眼相关部分作为补充背景，不是必需依赖

## 流程

### 1. 询问变更类型
新功能 / 修复 bug / 优化，三选一。

### 2. 确定版本号

以 `.claude/CLAUDE.md` 的「当前版本」为基线（`versions/` 里 v1.0.20 ~ v1.0.22 因 2026-11-02 的轻量流程断档，2026-11-12 起恢复逐版建档），结合步骤 1 的变更类型建议下一个版本号。

**版本号格式**：`v<major>.<minor>.<patch>`（如 v1.0.1）
- `major`：大版本，不兼容的 API 变更或重大重构
- `minor`：新功能、新模块、新接口
- `patch`：bug 修复、文档更新、小优化

**确定流程**：
1. 读取 CLAUDE.md 的当前版本号（如 v1.0.22）
2. 根据步骤 1 的变更类型建议下一个版本号（如 bug 修复 → v1.2.4，新功能 → v1.3.0）
3. **必须询问用户确认**：「本次变更类型为 X，版本号建议 vX.Y.Z，是否同意？或指定其他版本号」
4. 用户确认后使用该版本号

**注意**：不要自动决定版本号，一定要问用户。

### 3. 选择模块 —— 主动帮用户定位，不是甩清单

用户可能自己也不确定这次改动属于哪个模块，不要指望用户准确回答，要主动帮忙：

- 用户已经清楚说了模块 → 确认一下即可
- 用户描述了需求但没说模块 → 从描述里提取关键词，匹配 `index.md`，命中就报给用户确认；命中多个就都列出来问哪个/是不是都要动
- 用户完全不确定 → 先简单问一下这次大概要做什么，结合关键词匹配 + 列出候选模块的职责简述（读各 `module.md` 第一段），帮用户判断该归到哪个模块，或者判断这是不是需要新建模块
- 涉及多个模块 → 都记下来，后续每个都要更新

**读取模块复杂度元数据**：`index.md` 的模块表格中，`complexity` 列标记了模块的复杂度等级。识别命中模块的 complexity 后，按对应等级执行后续步骤的特殊处理（如 `high` 模块的 Hard Gate 等）。

新建模块时，先判断这是不是真的独立业务模块，还是应该归为基础设施（走 rule-skill 而不是模块）——判断标准见 `project-skill-manager` 的说明：路由/日志/上传/DB引擎/第三方SDK封装/公共扩展/前端基类这类不算模块。真的是新业务模块的话，骨架生成逻辑跟 INIT 一致：`module.md` + `business-logic.md` + `changelog.md`，按需加 `api-miniprogram.md` / `api-admin.md`。

**涉及新模块或代码落位不确定时**，通过 Skill 工具调用 `rule-layering`，按分层约定确定文件放置位置。

### 4. 读取模块历史上下文

两级读取，按需加载，避免一次性吞入无关内容：

1. **先读 `module.md`**（通常很短，包含文件路径、依赖关系、复杂度标记）
2. **再读 `business-logic.md` 的相关区块**：根据步骤 3 确定的模块范围和用户初步描述，只读取与本次改动相关的 `<!-- block: ... -->` 区块，不逐行读全文件。如果用户描述太模糊无法定位区块，则读 business-logic.md 的标题结构（`## ...` 行）列出区块清单让用户指认

### 5. 多轮对话商讨需求 —— 这是核心环节，不是一次性问答

基于模块历史上下文，跟用户展开真正的讨论，直到双方对"这次具体要做什么"达成一致，包括但不限于：
- 具体的业务规则/流程是什么，跟已有逻辑（尤其是同模块内相关区块）会不会冲突或重叠
- 边界条件、异常情况怎么处理
- 如果是 bug 修复，先确认根因，不要跳过分析直接改
- 如果涉及多端（小程序 / H5），各端分别要不要变、要不要保持一致
- 不要在需求还没聊清楚的时候就跳去写代码/建文档——宁可多问几轮，也不要靠猜

**固定顺序（2026-11-24 定版：别跳步、别重复"复述"）**：
① 逐轮收集材料（见下「逐轮问询模式」）→ ② 覆盖检查（六要素齐没齐）→ ③ 7 段需求总复盘 → ④ 用户确认/修正 → ⑤ 安全敏感（支付/退款/脱敏/鉴权）调 `rule-security` → ⑥ 落盘 `versions/vN/requirement.md`（此后才写代码）。任何一步都可以长聊，出口只有一个：⑥ 完成。

**逐轮问询模式（2026-11-24 定版：新需求默认按这个节奏，不要等用户提醒）**

用户可能分多轮、每轮给一张图或多张图 / 一段文案 / 一次补充说明；每轮只消化当轮材料，不跨轮提前自动补全需求。

- 每轮固定三步：
  1. **先复述理解，再提问**：把当轮材料按「页面/入口」「字段/文案」「状态/流转」「异常/边界」四类翻译给用户核对；图里的中文文字一律标「示意名」，字段名/枚举值以接口文档与代码实源为准。
  2. **只问当轮阻塞实现的问题**：每题给选项 + 推荐答案，每轮 ≤5 个按阻塞优先级排序；图里**没画**的（空态、无权限、失败回退、取消入口）必须主动问，不能默认"不存在=不做"。
  3. **回答落成编号口径**（`1.` `2.` …）：后续只引用编号，不重复问已确认项；用户改主意只重开对应编号，其余不动。
- **一轮多张图**：先对「图片台账」（图号 + 认领关系：主页面 / 弹窗 / 空态 / 不同平台 / 同一流程的不同步骤），复述顺序确认后逐张解读；同一流程的多张图先串成流程线（入口 → 操作 → 反馈）；**小程序端与 H5 端、本仓与另一客户端仓的图分开解读、分开登记，不混成一份口径**；后给的图与旧图/已确认口径冲突时先报冲突让用户裁决，**禁止自行用后图覆盖前图**。
- 轮次不设上限。六要素（用户故事 + 入口 + 字段 + 状态流转 + 异常兜底 + 多端差异）覆盖后做**需求总复盘**；未确认前不写 `requirement.md` 半成品。

**需求总复盘（2026-11-24 定版：材料收完后整体走一遍，不是把编号念一遍）**

**一次完整输出**，用户整体确认或指出要改的段，只对分歧段追问；任何一段改了，联动修正受影响的其他段。

- **新需求 / 涉及口径变化** → 7 段：① 一句话目标 ② 流程主线（按平台/端各一条，标出交互点）③ 口径清单（按主题分组，每条标来源：图N / 用户口述 / 推断待确认）④ 矛盾与缺口（材料冲突、图里有但口径没覆盖、口径互斥/强依赖）⑤ 与存量逻辑的关系（对照 `business-logic.md` 区块，标明新增 / 扩展 / 覆盖替换 / 废弃）⑥ 影响面（页面 / 组件 / composable / api / 配置 / 权限 / 多端）⑦ 剩余待确认项（编号 + 推荐答案）。
- **bug 修复 / 纯优化、不引入新口径** → 4 段：① 根因（复现路径 + 触发条件）② 影响面（页面 / 接口 / 状态 / 存量）③ 回归范围（要复测哪些既有流程）④ 是否触及已有口径（**触及就升级回 7 段**）。
- 复盘确认后落盘 `versions/vN/requirement.md`（7 段版落「口径清单 / 与已有逻辑关系 / 影响面」小节；4 段版落「背景 / 根因 / 影响面 / 回归范围」）。

**涉及支付/退款/脱敏/鉴权等安全敏感需求时**：按顺序 ⑤ 通过 Skill 工具调用 `rule-security`，在需求定稿前纳入，不要等落盘后补。

**中途退出/跳转**：商讨过程中如果发现需求不成立、需要重新定位模块、或用户改变主意，回到步骤 3 重新选模块，或直接终止流程（用户说了算）。

### 6. 扫描 rule-skill 清单，后续各阶段按需调用

查 `skills-index.md`，快速识别本次需求涉及哪些 rule-skill，**告知用户清单即可，不要在此步骤全部读完**。后续各阶段遇到对应场景时，通过 Skill 工具按需调用，保证规则内容在写代码时新鲜可用。

各 rule-skill 的具体触发时机以 `skills-index.md` 的「使用说明」表为准（那里维护「阶段 → 触发场景 → 调哪个 skill」的对照，是唯一真相源，本文件不再硬编码一份以免漂移）。

没有覆盖到的基础设施用法，正常写，不用等 rule-skill 补齐。

### 7. 检查子任务委托 + 复杂模块硬门槛

**子任务委托**：看当前已装的其他 skill 里有没有更适合处理这次某个子任务的（比如专门做测试用例生成、样式/组件生成的 skill），有就按需引用交给它处理，自己不大包大揽。

**复杂模块硬门槛**：如果命中模块的 `complexity` 为 `high`（见 `index.md` 的 complexity 列），该模块有独立的参考文档体系，开发前必须读其入口文档 + 按需子模块（见对应 skill 的说明），代码写完后（步骤 10 收尾阶段）必须调用对应 skill 同步文档，不要跳过。

## 开发流程

### 8. 开发过程中实时同步业务逻辑
边写代码边判断这次改动对应 `business-logic.md` 里的哪个区块，按风险分级确认：

- **高风险**（修改已有核心业务逻辑区块）→ 定位到该区块，**以 diff 格式展示新旧内容对比，用户确认后才落盘**
- **低风险**（新增枚举值、补充字段说明、新增独立区块）→ 可攒 2-3 个一起展示，批量确认，不必逐条来回

接口有变化 → 更新模块 `api-miniprogram.md`（活文档），不并入日志。

不要攒到最后一次性补文档——改一点、确认一点、落盘一点。

**写代码时按需调用 rule-skill**：遇到对应场景时（新页面 / 组件、请求链、配置项、登录态 / 守卫、上传、样式 token、新文件等），通过 Skill 工具即时调用对应 rule-skill，不要靠记忆或 CLAUDE.md 摘要。具体「什么场景调哪个」以 `skills-index.md` 的「使用说明」表为准。

### 9. 编译验证
代码写完后，执行双端编译验证（本项目唯一验收标准）：
```bash
npm run verify:mp-weixin && npm run verify:h5
```
两端都通过才能进入收尾。产物在 `dist/build/<平台>`（dev 环境包）。

**需要写测试时**，通过 Skill 工具调用 `rule-testing`，按 table-driven 模板和 Mock 约定生成测试代码。

### 10. 收尾，写入版本目录

创建 `.claude/project-meta/versions/vN/`：

- `requirement.md`：步骤 5 已落盘，这里只复核补最终版——背景、最终确认的需求、排除掉的方案（避免以后重复讨论已否掉的思路）、真机待验项
- `CHANGELOG.md`：变更类型、涉及模块、改了哪些区块（block id）、风险等级、是否需要数据迁移、代码变更表
- 契约有更新时，把后端对应版本的 `api-miniprogram.md` 与增量文档**逐字节副本**留档为 `api-miniprogram.md` / `api-*.md`
- 同步更新涉及模块的 `api-miniprogram.md`（活文档，按接口维度更新对应区块）

**涉及 `complexity: high` 的模块**：必须按步骤 7 的硬门槛调用对应 skill 同步参考文档，按变更范围只更新受影响的子模块文件。

### 11. 回写模块索引
在涉及模块的 `changelog.md` 追加一行：`版本号 | 日期 | 类型 | 一句话概述 | 改了哪些区块 | 链接到 versions/vN/`。

### 12. 实现后同步更新版本 meta
代码写完、编译通过后，**必须回到版本目录做最后一轮文档补全**：

1. 更新 `versions/vN/CHANGELOG.md` 的代码变更表——补齐步骤 8 可能漏记的文件
2. 更新 `versions/vN/requirement.md` 的最终口径——字段列表、数据来源、实现取舍
3. 同步涉及模块的 `business-logic.md` / `module.md`（若涉及业务逻辑变更）

目的是让 `requirement.md` 与 `CHANGELOG.md` 反映**最终落盘后的完整状态**，而不是需求商定时的初稿。

### 12.5 评审（双窗口循环，最后一步）

> **完整流程（角色 / 分级 / 报告模板 / `.last-sync` 基线处理）以
> `.claude/project-meta/review-process.md` 为唯一真源**；本节只保留触发与最小步骤，两者冲突时以该文件为准。
>
> `.claude/agents/reviewer.md` 的口径：**评审若执行，reviewer 必须是最后一步**。角色：**代码窗口**（本窗口）+ **评审窗口**（用户在本仓另开的独立会话）。评审窗口只审不改；代码窗口不自评。
> **用户交互规则（2026-11-24 用户定版）：提问只发生在代码窗口，且只有三种——① 是否开始评审；② 修复后是否复评；③ 评审结果里需要用户定口径的条目。评审窗口不直接问用户；纯技术性发送（首轮派发 / 修复指令 / 复评请求 / 通过回执）都不问，直接发。**
> **硬规则（定死，2026-11-24）：首次评审必须在用户新开的独立窗口里做**——禁止代码窗口自评、禁止复用其它已开会话或旧版本 / 上一轮留下的评审窗口。复评留在本版本的评审窗口；窗口关闭后复评必须重新新开。

触发：步骤 9 双端 `verify:*` 通过 + 步骤 12 版本 meta 更新后。

**第 1 轮：代码窗口发起**

1. **问 ①**：「要做评审吗？要做请在本仓（wxapp_c_template）新开一个 Claude 窗口，开好回我一声」。不做 → `versions/vN/CHANGELOG.md` 记 `评审：跳过（用户确认）`，进步骤 13。
2. 用户开好后，用 `ListAgents` + `SendMessage` 直接把指令发过去（本机找不到会话 → 回退成一行让用户手工粘贴）：
   - 目标 = 本仓、用户本次新开的评审会话；排除当前会话自己与任何旧评审会话；确认不了是不是刚新开的，先问用户
   - 指令 = `读 <本仓绝对路径>/.claude/skills/project-dev/SKILL.md 步骤 12.5、versions/vN/requirement.md、versions/vN/CHANGELOG.md，对 <base>..<head> 按 .claude/agents/reviewer.md 的口径评审，只出报告不改代码；发现的问题全部发回代码窗口 <本会话名>，标注代码级/需用户定`
   - `<base>` = `.claude/project-meta/.last-sync` 的 hash，`<head>` = 当前 HEAD（**评审 / 复评前代码窗口须先提交**；未提交改动不在范围内）

**评审窗口侧（每轮，全程不问用户）**

3. 按 `.claude/agents/reviewer.md` 审 `<base>..<head>`；报告写 `versions/vN/review.md`（复评 `review-r2.md`、`review-r3.md`…），按**阻断 / 建议**分级 + `文件:行号`，每条再标 **`代码级`** / **`需用户定`**。
4. **所有条目一次性 SendMessage 发回代码窗口**（编号 + 文件:行号 + 期望改法），不贴整份需求、不直接问用户；判断不了的不要猜，标 `需用户定` 发回。
5. 通过（无阻断项）→ 直接回发「评审通过（review.md）」给代码窗口。

**代码窗口侧（每轮）**

6. 收到清单：`代码级` 条目直接改（不问）；`需用户定` 条目汇总成一次提问给用户（这就是 ③），拍板结论回写 `requirement.md`（本仓无 `open-questions.md`，不新建）。
7. 改完 → 步骤 9 双端 `verify:*` → 步骤 12 更新 meta → **确保改动已提交**（复评范围 `<base>..<head>` 只含已提交内容；用户未要求提交时，在复评请求里注明让评审窗口一并看工作区未提交 diff）→ **问 ②**「要复评吗？」→ 要 → 直接发复评请求给评审窗口（写明 `review-rN`）；不要 → 收口（CHANGELOG 记 `✅ N 轮，用户决定不再复评`）。
8. 按用户决定不修的条目，在复评请求里列明「未修 + 原因」。
9. 循环 3-8 直到：评审通过 / 用户接受遗留 / 用户叫停。

**收口**

10. 评审通过后直接更新 `versions/vN/CHANGELOG.md` 的「评审」小节（轮次 + 结论，如 `✅ 3 轮通过，遗留建议 x2`），进步骤 13，不再问用户。

### 13. 更新同步基线
提交后执行 `git rev-parse HEAD`，把哈希写入 `.claude/project-meta/.last-sync`（这次改动走了记录流程，不算漂移）。

## business-logic.md 的区块格式规范

```markdown
## 登录流程
<!-- block: login-flow | last-updated: v7 -->
用户通过手机号+短信验证码登录。验证码有效期5分钟，
同一手机号60秒内只能发送一次。登录成功签发JWT，
有效期2小时，刷新Token有效期7天。涉及短信发送封装，
用法见 rule-sms-gateway。
```

- 每个区块一个 `block id`（英文短横线命名，模块内唯一，定了不要改名，业务文档与 commit message 会引用它）+ `last-updated` 版本号
- 描述中如果用到了某个基础设施（第三方SDK、上传、日志等），点一句"用法见 rule-xxx"，不要把基础设施的使用细节铺陈在业务逻辑里
- 更新区块 = 定位替换全部内容 + 更新 last-updated；新增区块 = 追加新的 `## 标题` + block 注释
- 单文件超过约 400 行时拆成 `business-logic/<主题>.md` 多文件 + `business-logic/index.md` 索引，格式不变

新增或追加开发规则（"加一条 rule"、"把这个规则加到 skill"、"新建一个 rule-skill"、"rule 同步"）不在本 skill 里做，统一走 `project-skill-manager` 的 RULES-TO-SKILLS 流程（唯一权威入口）：

> 用 project-skill-manager 把规则转成 skill

它会收集规则来源 → 判断追加到已有 rule-skill 还是新建 → 用统一模板生成 → 登记 `skills-index.md`，且只处理新增/变更部分。本 skill 只负责在步骤 6 查 `skills-index.md` 并按需调用，不重复实现这套逻辑。
